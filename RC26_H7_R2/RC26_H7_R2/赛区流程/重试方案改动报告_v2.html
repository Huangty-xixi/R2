一、v1 方案回顾（已废弃）

v1 设计（2026-06-29 重试方案.html）

两阶段协议：第一次CH5脉冲中断+保存状态+回滚GetKFS→进入ARM中间态→第二次脉冲重启
两种类型：武馆重试(CH5 max→mid) / 对抗区重试(CH5 min→mid)
核心问题：

  • retry.c/retry.h 从未实现——整套方案只是HTML文档
  • Process_GetKFS_AbortAndRollback 没写——GetKFS中途中断无法正确回滚
  • ARM中间态无超时——飞手忘记发第二次脉冲=死局
  • 两阶段操作太慢——竞赛中飞手压力大，繁琐
  • 只区分武馆/对抗两种类型，二区和一区的重试混在一起
  • 执行顺序依赖（AbortAndRollback必须在ResetAll之前）脆弱

结论：废弃。改 v2。

二、v2 方案：操作流程

核心交互

飞手用 CH5 拨杆 拨 N 次（1~4次）选重试类型， 看着 蜂鸣器 响 N 声确认没数错， 然后拨 CH7 到最高 确认执行。

1拨CH5计脉冲
CH5高位→回中=1次脉冲。3秒窗口内可以继续拨。每次拨蜂鸣器响一声确认收到。
2蜂鸣器反馈
3秒无新脉冲→锁定计数。蜂鸣器每1秒响N声（N=脉冲数）。飞手听响声判断有没有数错。
3CH7确认
飞手确认蜂鸣声正确→拨CH7到最高→开始执行重试。5秒无确认→超时取消。
4执行重试
断电→初始化执行器→等2秒→恢复数据→启动对应流程。执行完回到IDLE。

取消方式

任何时候拨 CH7到最小 → 取消当前重试 → 回IDLE。
蜂鸣器反馈阶段5秒内不确认 → 超时自动取消。

脉冲次数蜂鸣器响声重试类型断电？特殊操作
1次 每1秒·响1声 一区重试 是 CH5 max→mid 一次，确认后CH7 max

3次 每1秒·响3声 三区预备重试 是 CH5 max→mid 三次，确认后CH7 max
4次 每1秒·响4声 三区重试 不断电！ 特殊序列：CH7 min → CH5 min×3 → CH7 max

三、四种重试：详细执行流程

一区重试 — 1次脉冲

断电：停所有电机，Process_Flow_ResetAll，odom_nav_goto_disarm，YawHeadingCtrl_Clear，ClampHeadCtrl_Init

执行器归位：kfs_spin_position = p1（前臂回安全位）

等2秒让电机物理到位

启动：AppZone1_Start()，app_flow_mode = app_flow_zone1。一区从头跑。

"不关电脑，直接断电" — 不关NUC主控。断电只是电机/驱动器掉电。

二区重试 — 2次脉冲

断电：同上

初始化所有执行器（2秒）：

  • 主轴 main_lift_position = p0
  • 上下伸缩 kfs_above/below_position = p1
  • 前臂 kfs_spin_position = p1
  • 大风车 three_kfs_position 不动（一区结果保留！）
  • 吸盘全关（安全）

恢复数据：用之前R1收到的mission数据（Retry_SaveMission保存的副本）→ app_zone2_mission_apply()

启动：app_flow_mode = app_flow_zone2

注意宏开关：
技能赛Z12 → 梅林就停，不上坡
竞技赛 → 走完路径后还要上坡

三区预备重试 — 3次脉冲

断电：同上

重拿KFS：three_kfs_position归p1（大风车回到只拿了一个桩的状态）

初始化：主轴p0 → 上下伸缩p1 → 前臂p1

不上坡：跳过upslope，车已在地面

导航G1的同时同步初始化执行器：

  • 导航到G1的路上：main_lift→p2（取KFS高度）
  • kfs_spin→p2（转臂到取KFS位置）
  • kfs_above/below 到位

G1取KFS → 导航G2 → 取G2 → AppZone3_Start

三区重试 — 特殊序列

不断电！硬件不动，只做软件重置

流程：

  • Process_Flow_ResetAll()
  • odom_nav_goto_disarm()
  • YawHeadingCtrl_Clear()
  • flow_mode = app_flow_mode = none
  • AppZone3_Start()
  • app_flow_mode = app_flow_zone3

适用场景：车和R1撞一起了，偏离位置。不需要重新初始化硬件，只需要重置流程重新导航到三区入口。

为什么独立序列：三区重试不断电，需要一个明确的"我不会断电"信号（CH7 min → CH5 min×3 → CH7 max），和断电类重试区分开。

七、遗留：GetKFS_AbortAndRollback 是否还需要？

v2方案对这个问题的影响

v2方案的核心是"断电+重新初始化"而非 v1 的"中断保存状态→ARM→恢复状态"。

一区/二区/三区预备重试都先"断电"——所有电机停掉、Process_Flow_ResetAll清零get_kfs_step、执行器重新归位。

这意味着 v1 设计中最复杂的"GetKFS中途中断→回滚three_kfs_position和吸盘"问题在 v2 中基本不出现——因为直接断电重来了，不需要中途保存和恢复。

但仍需要的情况

三区重试（不断电） 仍然可能遇到GetKFS进行中。但三区重试只发生在"撞一起了"的极端场景，且三区重试的"AppZone3_Start"会执行Process_Flow_ResetAll清掉get_kfs_step。

不过如果三区预备重试（AppZone3Prep_StartFromP1）被调用时GetKFS恰好busy（概率极低），需要reset。

建议

场景是否需要AbortAndRollback理由
一区/二区/三区预备重试（断电类）不需要Process_Flow_ResetAll已清get_kfs_step
三区重试（不断电）可加，非必须ResetAll也清零了，加它主要是恢复吸盘状态
三区预备重试 StartFromP1 时GetKFS busy建议加防御性：AppZone3Prep_StartFromP1内部调用ResetAll前加判断

结论：v2 方案大幅降低了GetKFS_AbortAndRollback的必要性。建议实现一个简化版——只负责关busy标志和恢复吸盘状态，不涉及复杂的three_kfs_position回滚（反正断电后要重新初始化到大风车归p1）。

八、v2 新方案场景推演

A类：操作手按对了——正常流程

1一区重试，一切正常
飞手拨CH5一次→蜂鸣一声→拨CH7 max→车断电→上下伸缩归位→前臂归位→等2秒→AppZone1_Start从头跑。流程干净。
2二区重试，3个KFS已取完，第4个卡住
飞手拨CH5两次→蜂鸣两声→确认CH7 max→断电→主轴/上下伸缩/前臂归位(大风车保留一区结果)→等2秒→恢复R1 mission数据→app_zone2_mission_apply()→从Z2_ENTRY_NAV重走路径。调度器自动跳过已完成的桩。
3三区预备重试，要从G1重拿KFS
拨CH5三次→蜂鸣三声→CH7 max→断电→大风车归p1→主轴/上下/前臂归位→等2秒→AppZone3Prep_StartFromP1→skip upslope→导航G1→路上主轴到p2/前臂到p2→G1取KFS→G2取KFS→AppZone3_Start。
4三区重试（撞一起了），用特殊序列
CH7拨min→CH5低位拨三次→CH7拨max→不断电→Process_Flow_ResetAll + odom_disarm→AppZone3_Start→直接进三区流程等R1命令。

B类：操作手动作偏了——边界行为

5拨了3次CH5，犹豫后发现是2次才对，拨CH7取消重来
蜂鸣器正在响3声的pattern。飞手拨CH7 min→IDLE→清零。重新拨CH5两次→蜂鸣两声→CH7 max→执行二区重试。
6拨了CH5后忘了拨CH7，愣着超过5秒
蜂鸣器响了5秒→超时自动取消→回IDLE。飞手需要从头再来。
7拨CH5慢吞吞，第1次和第2次隔了5秒
3秒窗口在第1次脉冲后开始。如果5秒后才拨第2次→窗口已过期→第1次已进入FEEDBACK（蜂鸣1声）→第5秒的第2次脉冲被忽略（FEEDBACK状态下不接收新脉冲）。飞手听到1声而不是2声→知道时间过了→CH7 min取消重来。
8拨了5次CH5（手抖了）
COUNTING状态下最多计数到4。第5次脉冲被clamp在4。蜂鸣器每cycle响4声。
9CH5电位器噪声/在阈值附近抖动
50ms防抖：距上次边沿<50ms的跳变被忽略。但如果噪声间隔>50ms（比如500ms抖动一次），会误触多次脉冲。建议加滞回：记录上次稳定值，在一定时间内变化回原始值则忽略。
10脉冲计数阶段，CH7不小心碰了一下
CH7 min（非max）→取消。CH7在中位不触发确认。只有CH7到max才确认。所以不小心碰了一下pos在中位不会触发。

C类：执行过程中出问题

11二区重试执行中又出问题，想再重试
RETRY_EXECUTING状态下不接收CH5/CH7事件。必须等当前重试完成。完成后回到IDLE，可以重新拨CH5。建议加全局重试次数限制防止无限循环。
12一区重试断电后等2秒，2秒内电机没到位
2秒是hardcode的等待。如果电机确实没到位（比如卡住了），一区重试仍然会启动。启动后夹爪/传感器检测不到就自然fail。
13三区预备重试导航G1的路上，里程计漂了
重试前ARMed期间车被撞、被推动、或者在斜坡上中断——odom定位已经漂了。导航到G1可能走错路。没有重定位机制。

D类：和R1通信的边界

14二区重试用的mission数据是新的还是旧的？
Retry_SaveMission在每次收到R1 mission时保存最新一份副本。如果比赛过程中R1发了新的mission（修正数据），重试会用最新那份。如果从未收到过R1 mission（比如还没走到二区），s_saved_has_mission=0→app_zone2_mission_apply不会执行→二区重试会因为没有mission数据而idle。
15重试执行期间R1又发新mission过来
Retry_SaveMission仍然会更新副本（覆盖旧的）。但重试已经在执行中不会重新读取——重试只读取一次。如果飞手在重试完成后又重新开始了一次重试，会用新的mission数据。

九、Scale Game 极端尺度推演

维度最小值最大值发现
脉冲计数 0次（拨CH5但没到阈值就松手） 无限（手抖乱拨） clamp在4。但COUNTING窗口每3秒刷新一次，如果连续几分钟乱拨→永远停留在COUNTING→永不进入FEEDBACK→不会有任何动作。虽然烦人但不危险
蜂鸣器响 0声（静音） 一直响（Buzzer_Beep被反复调用） Buzzer_Beep每次重新开始计时，不会累加。Service每tick检查超时就关。不会一直响
ARM等待 0ms（手速快，1秒内两次脉冲） ∞（忘了发第二种脉冲） v2没有ARM中间态。COUNTING→FEEDBACK自动流转。FEEDBACK 5秒超时。不会永久卡住 ✅
重试回合 1次 无限次 v2和v1一样没有全局重试限制。建议加计数器。最坏: 飞手反复拨CH5→重试→完成→再拨→无限循环
断电执行器初始化 0ms（instant） 几分钟（电机卡死） 2秒hardcode可能不够。如果电机确实卡死，硬等也没意义。建议加看门狗或超时保护
CH5抖动频率 0次/秒 100次/秒（噪声） 50ms防抖=最多20次/秒有效脉冲。如果抖得快→clamp到4→FEEDBACK→超时IDLE→又抖→重新COUNTING→循环。建议加连续重试冷却期(比如完成一次重试后10秒内不能重试)

十、Inversion 反转思维

原假设反转暴露的
"蜂鸣器只是为了确认" 如果没有蜂鸣器？ 飞手纯靠拨杆次数记数和猜测。竞技赛紧张环境下极容易拨错。蜂鸣器不仅确认，更是唯一反馈。如果蜂鸣器坏了=重试功能废了。建议：没有蜂鸣器时用LED闪烁替代或干脆禁用重试
"重试=断电重来" 如果重试可以不断电？ 三区重试就是不断电的例子——只软件重置。其他三种断电是因为需要物理归位。如果能通过传感器确认"执行器已在安全位置"，就可以省掉断电等待的2秒
"CH7确认是比较安全的" 如果不要CH7确认直接执行？ 少一步操作，但飞手没有最后检查的机会。蜂鸣器响错了也硬着头皮执行。两阶段（听→确认）提供了纠正窗口
"断电是软件复位" 如果断电是真的断电池？ 车体MCU可能重启。所有运行时状态丢失。重试数据备份在RAM也丢了。需要把备份写到Flash或EEPROM。但当前没有这个需求——断电只是"软件停电机"
"四种重试覆盖所有场景" 如果还可以有其他重试？ 比如"只重试导航到某个点"、"只重建传感器"、"只复位KFS"。当前的4种是粗粒度的，未来可能需要细粒度。设计时预留扩展点（Retry_Type枚举好加新值）

十二、Meta-Pattern 跨场景模式

模式出现次数抽象描述缓解
断电=软件复位≠真断电 3 代码里"断电"只是停电机+清变量。如果驱动器死了需要真断电的场景，软件无能为力 如果有GPIO控制继电器就真断电；没有的话在文档里明确"断电=软件复位"
mission数据版本一致性 3 重试时用的mission可能是旧的（R1发了新数据但重试已开始）、也可能是空的（从未收到过） 加版本号/时间戳/valid标志。重试前检查mission数据是否valid
执行器归位≠机械到位 4 设了position变量=软件认为"在p1"。但物理上电机可能没到位(卡住/断线/被外力挡住) 如果有位置传感器就用传感器确认；没有就接受2秒等待的不确定性
脉冲信号的脆弱性 4 CH5/CH7电位器在阈值附近的噪声、慢拨的多脉冲、周边电磁干扰 防抖+滞回+边沿检测方向限制(max→mid才计数, min→mid忽略)
状态机无看门狗 3 COUNTING/FEEDBACK/EXECUTING任何状态都可能卡住（逻辑bug）。没有独立监控 每个状态加timeout。EXECUTING加最大执行时间(如30秒),超时force回IDLE

十三、实现中需注意的细节

#问题说明
P0 TIM12时钟频率依赖HSE晶振 如果HSE不是24MHz(比如换成25MHz或8MHz板子),TIM12时钟会变,需要重算PSC/ARR。建议用宏从HAL_RCC_GetPCLK1Freq()动态计算或在注释里标明"检查HSE频率"
P0 AppZone3Prep_StartFromP1使用g_app_zone3_cfg前确认已初始化 g_app_zone3_cfg.g1_x_m/g1_y_m需要在使用前已被设置。正常情况应该没问题，但如果重试触发在zone3配置之前=崩
P1 二区重试的three_kfs_position保留逻辑 断电+初始化执行器时大风车不能归p1(一区取的圈在上面)。但上下伸缩和主轴归位时可能带动大风车。需要确认物理上是否独立
P1 三区预备重试的并行初始化 导航到G1的路上同时初始化执行器。实现方式：设目标位置变量→让manual_kfs_function自然驱动到位→不阻塞导航。需要一个"所有执行器到位"检查,在G1到达之前不依赖它们到位
P1 Retry_Service每tick调用不要影响实时性 Retry_Service中有switch/if、蜂鸣器状态机、执行逻辑。确认不会在关键路径上增加显著延迟(应<100us)
P2 重试期间CH5仍可用于取放桩？ Retry_IsActive/IsExecuting门控motion_route_channels→重试期间不能用CH5取放桩。合理(重试期间应该专注一件事)
P2 Retry_SaveMission的线程安全 r1_link.c中在中断上下文中调用Retry_SaveMission？需要确认是在任务上下文还是ISR。如果在ISR，memcpy可能太长。实际看代码是在UART接收回调中(中断),需要禁IRQ保护或改用原子操作
P2 蜂鸣器听感 无源蜂鸣器4000Hz很尖。100ms响+300ms间隔 = 2.5Hz节拍,飞手能听清。但竞技赛环境嘈杂(电机声/背景噪声),蜂鸣器可能听不见。建议留PWM占空比可调或预留LED同步闪烁

最终总结

v2 重试方案相比 v1，核心变化是——从"精细状态保存/恢复"改为"暴力断电重来"。
这大幅简化了实现复杂度，避免了 v1 中 GetKFS_AbortAndRollback 这个最棘手的函数。

新增的 蜂鸣器反馈 是用户体验的关键——让飞手在嘈杂环境中能确认自己的操作。

CH5脉冲计数 + CH7确认 的两阶段设计提供了取消窗口，比 v1 的 ARM 更直观。

实现时需注意：12个文件要改动（4新建+8修改），Keil工程要加源文件，TIM12频率要确认HSE晶振值。

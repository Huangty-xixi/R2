五、边界 & 极端场景推演

5ResetAll在AbortAndRollback之前P0
get_kfs_step→idle, s_get_kfs_busy→0。AbortAndRollback读busy=0→return。three_kfs不回滚，sucker不恢复。重启后KFS状态损坏不可逆。
6中断在PutKFS过程中P1
设计只调用GetKFS_AbortAndRollback，忽略PutKFS。Process_PutKFS_AbortAndRollback已实现但未被全局中断流程调用。吸盘状态可能不一致。
7一区重启未导航到一区起点P1
武馆重试zone1_done=false → AppZone1_Start()。若车在ARM期间被移动/在中场，AppZone1_Start可能远离一区区域。
8ARMED状态无超时P1
操作手忘记发第二次脉冲 → 车永远停在ARMED。motion_route_channels被屏蔽，无法执行任何操作。只能切CH8遥控退出。
9CH5慢速拨动多触发P2
边沿检测：ch5_bit==2 && prev!=2。慢拨产生2→0→2→0→2序列，每次产生脉冲。50ms防抖不足以完全防止。
10武馆重试在三区误触发P2
zone1_done=true + kfs_done_mask全满 → 车在二区路径上空转。设计说"武馆重试不管三区"，缺zone上下文检查。
11急停在ARMED期间
正常急停 → 关吸盘。但three_kfs_position未更新 → 软件认为还持有KFS，物理KFS已掉落。软件-物理解耦。
12ARMED没收第二次脉冲直接切遥控
motion_enter_remote() → ResetAll → 清所有状态 → 手动控制。设计预期行为。
13ARMED收到反方向脉冲
门控：武馆ARMED时收到min→mid(对抗区) → 忽略。反之亦然。正确设计。
14ARMED收到第三次同向脉冲
第二次触发RESTART，第三次及以后被忽略。正确设计。
15空闲时收到脉冲
门控：RETRY_NONE空闲时收到任何方向脉冲 → 忽略。正确设计。
16中断在导航中（运动状态）
odom_nav_goto_disarm() 发刹车指令 → 立即减速停止。非阻塞，正确。重启后从当前位置导航到目标。

六、Superpowers 思维注入

🎲 Scale Game — 极端尺度

维度最小最大发现
ARM持续0ms∞无超时→永久卡住
重试次数1∞无全局限制
中断时机空闲done瞬间最窄窗口=最大风险
失败率0%100%间歇失败最需要重试
中断速度1 tick多tick跨tick中间状态不一致

🔄 Inversion — 反转假设

"操作手总会选对类型" → 反转：可能误操作 → 场景22/23无zone校验

"两阶段最安全" → 反转：单脉冲突时更简单 → ARM中间态引入负担

"重试总能恢复" → 反转：可能更糟 → 累积机械误差

"中断<1 tick" → 反转：可能跨tick → 需确保原子性

⚡ Collision-Zone — 概念碰撞

重试 = 电路断路器
跳闸需瞬时、合闸需确认、反复跳合损坏设备

重试 = 数据库事务
ROLLBACK + 新事务。隔离性由RTOS单线程保证。

重试 = 视频游戏Checkpoint
保存关键状态→从Checkpoint重生。不全量保存。

🕸 Meta-Pattern — 跨场景重复模式

模式出现场景数抽象描述缓解策略
状态保存不完整 6 保存/恢复状态向量遗漏某个维度（如GetKFS回滚不覆盖PutKFS） 编写完整的状态清单检查表，每次中断遍历所有维度
顺序依赖脆弱 4 多步骤中断流程有严格偏序关系，错序导致破坏性后果 代码审查强制检查调用链顺序；加运行时断言
双阶段协议双刃剑 3 ARMED提供撤销能力但引入中间状态脆弱性（无超时、门控影响其他操作） 加超时退出、加LED指示ARMED状态
物理-软件状态解耦 3 致动器回滚是"尽力而为"，无法精确回到中断前物理位置 中断后重新校准传感器；加物理限位
CH5复用上下文依赖 3 s_match_auto_active切换时CH5功能语义变化，增加误触发风险 加强状态转换时的互锁检查

十、最终推演评估

🟢 设计亮点

  • 两阶段协议：中断与重启分离，给操作手撤销机会
  • GetKFS三轮通用回滚：start_three_pos自动适配，设计优雅
  • kfs_done_mask恢复：调度器自动跳过已完成桩，无需重走
  • 保留/清理清单明确：sucker/mission/last_seq 正确保留
  • CH5复用设计：s_match_auto_active自动切换，节省通道
  • 50ms防抖 + 门控规则：防误触发机制到位

🔴 关键不足

  • retry.c 未实现：整个全局重试方案的核心模块缺失
  • GetKFS_AbortAndRollback未实现：最复杂的回滚逻辑缺失
  • 无 ARM 超时：可能永久卡住
  • 一区重启无导航：可能从错误位置启动
  • 无全局重试次数限制：可无限次ARM→RESTART循环
  • CH5边沿检测不够严格：慢拨多触发隐患
  • 缺 zone 上下文校验：误操作无保护
  • PutKFS回滚被遗漏：设计只覆盖GetKFS

⛔ 一行总结

设计文档逻辑自洽，但 retry.c 未落地 + Process_GetKFS_AbortAndRollback 缺失导致全局重试方案当前不可用。
实现时需按 P0(2项)→P1(3项)→P2(3项) 顺序修复，最大的单一风险是 GetKFS done 边缘的 three_kfs_position 与 kfs_done_mask 不一致窗口。

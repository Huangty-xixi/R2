📖 三、逐状态详解

[1] nav_turn_open — 导航到开放目标 + 转向90°

项目内容
入口AppZone1_Start() 调用后，导航到 (open_target_x_m, open_target_y_m) + Yaw 90°
红方→FIELD_RIGHT(-90°)，蓝方→FIELD_LEFT(90°)
每帧peek导航结果，等 YawHeadingCtrl_ParallelLegSettled() + nav_leg_done() 同时满足
出口-成功导航到达+转向稳定 → [2]reverse_slow_to_limit
出口-失败odom失效(BAD_CONFIG/ODOM_READ) → [8]abort
超时(15s) → [8]abort
每帧pre-switch odom检查失败 → [8]abort

[2] reverse_slow_to_limit — 后退靠边检测

项目内容
入口从 nav_turn_open 成功到达后
每帧施加 VY = -forward_slow_cmd(-40.0)，检测堵转：
|VY| >= 2.0 且 堵转轮数 >= 3 且 持续 180ms
出口-成功堵转检测触发 → [3]shift_right_monitor
出口-失败超时(6s) → [8]abort (无FLOW_THROUGH逃生)
特殊不检查odom (不属于 nav_odom 依赖状态)

[3] shift_right_monitor — 扫矿监控

项目内容
入口从 reverse_slow 堵转检测 / clamp重试 / 双圈第二圈
每帧核心扫矿逻辑 run_grab_monitor()：
• 夹爪 idle→closing 转换检测 → latch → 进clamp_wait
• 视觉Y坐标在 [y_lo, y_hi]区间内: 累计stable_ticks，允许自动夹取
• 超出上/下界: flip扫方向 + pull_back减速
• 速度控制: margin减速 x anchor减速(min 0.6)
• Y区带滞回(6区: below/lo_band/mid/hi_band/above + unknown)
出口-成功夹爪 latch → [4]shift_right_clamp_wait
出口-超时15s超时: FLOW_THROUGH=1 → [5]advance_turn180(跳过夹取)
FLOW_THROUGH=0 → [8]abort
出口-失败每帧pre-switch odom检查失败 → [8]abort

[4] shift_right_clamp_wait — 等夹爪完成

项目内容
入口从 shift_right_monitor 夹爪latch后
每帧轮询 ClampHeadCtrl_GetState()：
• dock_ok → clamp_wait_exit_success
• upright_hold + 物体存在 + 持续2s → clamp_wait_exit_success
• idle + 物体不在 + 持续200ms → 重试(最多8次)或FLOW_THROUGH
• 超时30s: FLOW_THROUGH=1 → exit_success; 否则 → abort
出口-成功→ clamp_wait_exit_success()
单圈/双圈第一圈: → [5]advance_turn180
双圈第二圈(skill_lap!=0): → [7]done 直接
出口-重试物体丢失 + 重试次数<8 → [3]shift_right_monitor
出口-失败重试耗尽 + FLOW_THROUGH=0 → [8]abort

[5] advance_turn180 — 转180°返回

项目内容
入口从 clamp_wait_exit_success / FLOW_THROUGH跳过 / 双圈第二圈开始
每帧Yaw 180° PostCommand + 导航到 (return_target_x_m, return_target_y_m)
等 YawHeadingCtrl_ParallelLegSettled() + nav_leg_done()
出口-成功单圈/双圈第一圈: → [6]wait_r1_release
双圈第二圈(skill_lap!=0): → [3]shift_right_monitor(回去扫第二圈)
出口-失败yaw180命令失败 / odom错误 / 超时15s → [8]abort

[6] wait_r1_release — 等R1任务帧 V4 改造

项目内容
入口从 advance_turn180 完成(单圈/双圈第一圈)
每帧1. 清除运动override
2. 检查 r1_pending != 0 → 退出
3. 可选超时(5s, 需 WAIT_R1_TIMEOUT_ENABLE=1)
r1_pending
设置机制		每帧在Run()开头调用 app_zone1_poll_r1_release_sig()：
if (R1Link_HasNewMission()) AppZone1_NotifyR1Release();
AA..BB任务帧一到 → r1_pending=1

重要：r1_pending可以在任何状态被提前设置(比如zone1还在扫矿时R1就发了任务)，但只在本状态被检查消费。提前设置→进入本状态时立即可退出。
出口→ wait_r1_exit(now_ms, 1U):
单圈: NotifyDockOk()松爪 → [7]done
双圈第一圈(skill_lap==0): NotifyDockOk()松爪 → skill_lap=1 → ClampHeadCtrl_Init() → [5]advance_turn180(第二圈)
卡死风险⚠ 无R1发AA..BB + WAIT_R1_TIMEOUT_ENABLE=0 → 永久卡死。CH7单独调试时必现。
逃生: CH7下降沿手动中断 / 开超时宏 / R1配合发任务帧

[7] done — 完成

清除底盘overide，设 active=0/done=1/failed=0，回到idle。
Motion_Task检测到done → 比赛模式自动切zone2，调试模式切none。

[8] abort — 异常中止

清除底盘overide，设 active=0/done=0/failed=1，回到idle。
Motion_Task检测到failed → 比赛模式仍然切zone2(容忍一区失败继续二区)，调试模式切none。
📡 四、R1任务帧触发松爪 V4 改造

改造前 (CC..DD)

R1 → USART10 → CC..DD(4B) → r1_link_sig → R1Link_TakeSig() → r1_pending=1
问题：对接成功需要R1发两条指令(CC..DD + AA..BB)，多余。现已全部删除。

改造后 (AA..BB)

R1 → USART10 → AA..BB(7B) → r1_r2_connect_decode → s_has_new=1
→ poll_r1_release_sig() 检测 R1Link_HasNewMission() → r1_pending=1
→ wait_r1_release 退出 → NotifyDockOk() 松爪
→ 切zone2后 motion_poll_zone2() 调用 R1Link_TakeAndApply() 消费同一帧

时序安全分析

场景行为安全?
R1在扫矿时提前发AA..BBr1_pending提前=1，但只在wait_r1_release状态被检查。松爪仍发生在导航返回后✅ 安全
R1在夹爪完成前发AA..BB同上，r1_pending提前设置不影响夹持流程✅ 安全
未夹到物体时AA..BB到达NotifyDockOk受state==upright_hold守卫，夹爪state不对时空操作✅ 安全
AA..BB帧在zone1 abort后残留s_has_new未被消费，但zone1已reset(r1_pending=0)。下次zone1启动时不会误触发⚠ 低风险
R1不发AA..BB永久卡死在wait_r1_release(除非开超时宏)❌ 卡死

🔀 六、关键分支点

① clamp_wait_exit_success() — 夹爪完成后的分支

SKILL_MODE=1 + skill_lap!=0(双圈第二夹完成):
→ enter_done() 直接完成，不走advance_turn180，不走wait_r1_release
机器人停在扫矿位置，不回return_point。需确认赛事规则是否允许。
其他情况(单圈 / 双圈第一夹):
→ enter_advance_turn180() → wait_r1_release → ...

② wait_r1_exit() — 收到R1任务帧后的分支

SKILL_MODE=1 + skill_lap==0(双圈第一圈完成):
→ NotifyDockOk()松爪 → skill_lap=1 → ClampHeadCtrl_Init() → advance_turn180 → 第二圈扫矿
非SKILL_MODE / skill_lap!=0(单圈 / 双圈已完成):
→ NotifyDockOk()松爪 → enter_done()

③ advance_turn180 — 转180完成后的分支

SKILL_MODE=1 + skill_lap!=0(双圈第二圈开始):
→ grab_monitor_begin() → shift_right_monitor(回去扫第二圈)
其他情况:
→ clear motion → wait_r1_release
⚙ 七、关键配置宏
宏默认值影响

🚨 八、已知问题与边界情况
🔴 HIGH — CH7单独调试zone1时永久卡死
场景：CH7单触发zone1，无R1配合。zone1完成夹取后进入wait_r1_release，无AA..BB帧到达+WAIT_R1_TIMEOUT_ENABLE=0 → 永远卡住。
逃生：CH7下降沿手动进 mission_clear / 开超时宏 / R1配合发任务帧。
注：此问题改造前就存在(原来等CC..DD也是同理)，非本次改造引入。
🟡 MEDIUM — s_has_new在zone1 abort后未清理
场景：zone1收到AA..BB(s_has_new=1) → zone1因超时abort → r1_pending被清零但s_has_new留着 → zone1重进wait_r1_release时误判"新任务到了" → 虚假松爪。
缓解：Motion_Task调度zone2时TakeAndApply会消费s_has_new。但若zone1 reset后立刻重入(不上zone2)，则触发虚假信号。
修法：AppZone1_Reset()中增加消费残留任务帧的逻辑。
🟡 MEDIUM — Z12第一圈 NotifyDockOk + ClampHeadCtrl_Init 冲突
wait_r1_exit中先调NotifyDockOk(舵机→upright)，立即又调ClampHeadCtrl_Init(舵机→mid)。Init覆盖upright。
功能无实际损害(夹爪保持张开)，但逻辑冗余。
🔵 LOW — 双圈第二圈clamp完成后直接done，不松爪
clamp_wait_exit_success中skill_lap!=0时直接enter_done，不经过wait_r1_release，不调NotifyDockOk。
第二圈抓到的矿物停留在爪中，zone1直接完成。如果赛规要求第二次也通过R1释放，需修改。
🔵 LOW — R1Link_ErrorRecover不重置s_has_new
通信异常恢复后可能残留旧任务标志，导致虚假的HasNewMission()=true。
🔵 LOW — CC..DD帧残留字节可能误触发55..AA/EE..FF帧
删除CC..DD分支后，收到CC..DD帧时其数据字节会被后续55..AA/EE..FF的feed_byte误解析。极低概率形成有效假帧。
实际影响极小(需3字节凑成有效校验和)。
🔵 LOW — grab_ticks_thr_boundary默认值0被校验拒绝
AppZone1_SetConfig()校验要求 boundary>0 且 center>0，但默认值boundary=0。调用SetConfig(&default)会失败。
不影响现有流程(目前没有调SetConfig的地方)。

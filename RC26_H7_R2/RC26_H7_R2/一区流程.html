R1任务帧触发与消费机制 V5双重防止重复消费

V4遗留问题：AA..BB帧可能被重复消费

V4中 r1_pending 被消费后没有清除底层 s_has_new 标志，也没有防止同一帧被zone1再次消费。
场景：zone1收到AA..BB → r1_pending=1 → 消费后zone1 abort → zone1重启 → s_has_new 仍然为1 → 误判"新任务"。
V5通过 z1_mission_handled + R1Link_ClearNewMission 双重机制解决。

V5 消费流程

第1层守卫 — z1_mission_handled (app_zone1.c 局部)：
app_zone1_poll_r1_release_sig():
  if (R1Link_HasNewMission() && (g_app_zone1_ctx.z1_mission_handled == 0U))
      AppZone1_NotifyR1Release(); // → r1_pending = 1
第一圈消费后 z1_mission_handled=1 → 不再触发 r1_pending
第二圈开始前在 wait_r1_exit 中 z1_mission_handled=0 → 允许再次触发

第2层守卫 — R1Link_ClearNewMission (r1_link.c 全局)：
wait_r1_release 退出时：
  g_app_zone1_ctx.z1_mission_handled = 1U;
  R1Link_ClearNewMission(); // s_has_new = 0
  app_zone1_flow_wait_r1_exit(now_ms, 1U);
双重保障：即使 z1_mission_handled 被意外清零，s_has_new 也已清除

正常时序（双圈）：
1. R1发AA..BB(第一帧) → s_has_new=1 → z1_mission_handled=0 → r1_pending=1
2. wait_r1_release 消费: z1_mission_handled=1, R1Link_ClearNewMission()
3. wait_r1_exit: skill_lap=0→1, z1_mission_handled=0, 进入第二圈
4. 第二圈 wait_r1_release: R1发第二帧(或超时) → 再次消费 → done

⏱️ 超时保护机制 — dock_timeout_ms V6新增

设计目标

一区流程涉及 导航、靠边堵转、扫矿、夹爪、R1通信 等多个阶段，每个阶段都有局部超时（如导航15s、靠边6s、扫矿15s、夹爪30s、等R1帧5s）。
但存在局部超时仍无法覆盖的"硬卡死"场景（如导航odom失效未触发错误、夹爪机械故障无idle状态、R1通信彻底中断且超时宏关闭）。

V6 全局超时保底（dock_timeout_ms = 120000ms = 120s = 2min） 作为最后一道防线：
从 AppZone1_Start() 启动就开始倒计时，一旦到期，无论当前在哪个状态（除 wait_r1_release / done / abort 外），强制将流程拉入 wait_r1_release，走标准松爪退出路径。

核心代码

配置定义 (app_zone1.h)：
uint32_t dock_timeout_ms; /* 一区全局超时(ms),默认120s */

默认值 (app_zone1.c s_zone1_cfg)：
.dock_timeout_ms = 120000U, // 120s 一区全局超时

启动时初始化 (AppZone1_Start)：
g_app_zone1_ctx.dock_deadline_ms = now_ms + g_app_zone1_cfg.dock_timeout_ms;

每帧检测 (AppZone1_Run 开头，状态机switch之前)：
if (g_app_zone1_ctx.dock_deadline_ms != 0U &&
    now_ms > g_app_zone1_ctx.dock_deadline_ms &&
    g_app_zone1_ctx.state != app_zone1_state_wait_r1_release &&
    g_app_zone1_ctx.state != app_zone1_state_done &&
    g_app_zone1_ctx.state != app_zone1_state_abort)
{
    Process_Flow_ClearChassisOverride();
    odom_nav_goto_disarm();
    YawHeadingCtrl_ParallelLegSettleReset();
    g_app_zone1_ctx.r1_wait_start_ms = now_ms;
    g_app_zone1_ctx.r1_pending = 0U;
    app_zone1_flow_enter_state(app_zone1_state_wait_r1_release, now_ms);
}

全局超时 vs 局部超时对比

维度局部超时（各状态独立）V6 全局超时保底
超时时间6s~30s 不等120s（2min，可配置）
触发位置各状态的 case 分支内部状态机 switch 之前（Run()开头）
触发效果大部分→abort（少量FLOW_THROUGH→跳过继续）→ wait_r1_release → 松爪 → done/第二圈
覆盖范围单个状态内部所有非终态（1-6, 9号状态）
设计目标状态级别的正常容错最后安全网：确保机器人永远不卡死
可配置各超时宏独立dock_timeout_ms 一个变量统一控制（默认120s）
安全设计原则：
1. 保守默认值（120s）：远大于正常一区流程耗时（通常30-60s），仅在系统级异常时触发
2. 非破坏性：超时不走abort路径（不设failed标志），走标准松爪→done路径，后续zone2正常执行
3. 不影响正常流程：正常流程远快于120s，超时保底完全不介入
4. 可观测：g_app_zone1_ctx.dock_deadline_ms 可在Keil Watch中实时观察倒计时

AppZone1_Run() 开头的超时拦截 V6新增

每帧在状态机switch之前执行：
if (dock_deadline_ms != 0 && now > dock_deadline_ms && state ∉ {wait_r1, done, abort})
→ 清除所有运动/导航/Yaw状态
→ 重置 r1_wait_start_ms = now_ms (5s超时重新计时)
→ 强制进入 [6]wait_r1_release

这个拦截优先级高于一切：
• 高于每帧的odom pre-switch检查
• 高于每个状态内部的超时/错误检查
• 唯一不触发的情况是已处于 wait_r1_release / done / abort 中

wait_r1_exit() — V5核心分支 V5重构

收到R1任务帧或超时后的出口：

z1_mission_handled = 0; // 允许第二圈消费

单圈 / 第二圈完成 (skill_lap!=0)：
→ [7]done

V4行为：skill_lap!=0时直接enter_done
V5行为：统一调用 enter_advance_turn180()
包括第二圈clamp完成后也回原点再wait_r1_release
这意味着第二圈也会导航回return_target，再等R1(或超时)才done。

已知问题与边界情况 V6新增全局超时相关
HIGH — CH7单独调试zone1时永久卡死（同V4/V5）
场景：CH7单触发zone1，无R1配合。zone1完成夹取后进入wait_r1_release，无AA..BB帧到达+WAIT_R1_TIMEOUT_ENABLE=0 → 永远卡住。
V6缓解：即使WAIT_R1_TIMEOUT_ENABLE=0，120s全局超时保底仍可将流程从任何状态强制拉入wait_r1_release → 5s超时退出。但对于已在wait_r1_release内等待的情况，全局超时不介入（已排除该状态）。因此严格来说此问题部分缓解：如果卡在其它状态（导航/扫矿等），120s后保底生效；如果已到达wait_r1_release且超时宏=0，仍可能卡死。
逃生：CH7下降沿手动进 mission_clear / 开超时宏 / R1配合发任务帧。
HIGH — 第二圈需要R1第二帧或超时才能完成（同V5）
V5/V6双圈第二圈在clamp完成后走 advance_turn180 → wait_r1_release。
如果WAIT_R1_TIMEOUT_ENABLE=0，且R1不再发第二帧AA..BB，将卡死在第二圈的wait_r1_release。
缓解：确保WAIT_R1_TIMEOUT_ENABLE=1（默认FLOW_THROUGH=1时已启用）。
V6部分缓解：如果第二圈在wait_r1_release之前的阶段卡住（如导航/扫矿），120s全局超时会将其拉入wait_r1_release，但进入wait_r1_release后如果超时宏=0仍可能卡死。
FIXED in V6 — FLOW_THROUGH=0时任何状态卡死不再永久锁死
V4/V5中，如果FLOW_THROUGH=0（严格模式），扫矿卡死/夹爪卡死直接abort，最终zone2仍可执行。
但存在FLOW_THROUGH=0 + 局部超时未触发（如导航odom降级但不触发错误码）的"灰色卡死"场景。
V6解决了这个灰色地带：120s全局超时不分FLOW_THROUGH，到期一律强制跳转，即使严格模式也有逃生通路。
MEDIUM — dock_deadline_ms 在 AppZone1_Reset 中被清零
AppZone1_Reset() 将 dock_deadline_ms = 0U，这是正确的：重置后重新Start会重新设置。
但如果在一次流程中abort后未重新Start直接重入，dock_deadline_ms=0 不会触发超时检查。
风险低：abort后Motion_Task会切zone2，不会留在zone1。
MEDIUM — 2min超时保底可能过早打断第二圈
如果第一圈耗时接近120s（如长距离导航+多次重试），第二圈刚进入2-3秒即触发全局超时。
虽然保底机制让第二圈也走了wait_r1_release→松爪→done，但第二圈完全没有执行扫矿。
场景示例：第一圈导航卡顿用了100s，剩余20s不足以完成第二圈扫矿。
缓解：可通过 g_app_zone1_cfg.dock_timeout_ms 在Keil Watch中在线增大超时值来适应特定场地。
MEDIUM — 第一圈 NotifyDockOk + ClampHeadCtrl_Init 冲突（同V5）
wait_r1_exit中先调NotifyDockOk(舵机→upright)，立即又调ClampHeadCtrl_Init(舵机→mid)。
Init覆盖upright。功能无实际损害，但逻辑冗余。
MEDIUM — clamp_wait_exit_success 无分支，第二圈也回返点（同V5）
V4中第二圈clamp完成直接done，物体留在爪中。
V5/V6中第二圈clamp完成后走advance_turn180回return_target，再等R1超时才done。
如果赛规要求第二圈不需要回返点，需修改分支逻辑。
LOW — R1Link_ErrorRecover不重置s_has_new（同V5）
通信异常恢复后可能残留旧任务标志，导致虚假的HasNewMission()=true。
但zone1有z1_mission_handled守卫 + V6全局超时兜底，影响有限。
LOW — grab_ticks_thr_boundary默认值0被校验拒绝（同V5）
AppZone1_SetConfig()校验要求 boundary>0 且 center>0，但默认值boundary=0。调用SetConfig(&default)会失败。
LOW — CC..DD帧残留字节可能误触发55..AA/EE..FF帧（同V5）
极低概率形成有效假帧，实际影响极小。

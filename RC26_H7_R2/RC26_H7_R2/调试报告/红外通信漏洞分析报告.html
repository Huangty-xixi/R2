💥 核心发现：0xAA 同步字节冲突

1

0xAA 双重身份：Mission 帧头 ≡ Z3 Put 帧尾

R1_R2_connect.h:47 & r1_link_z3_put.h:21
致命
同一个字节 0xAA 在两个帧协议中承担不同角色——对 Mission 帧它是"开始"，对 Z3 Put 帧它是"结束"。两者共存于 USART10 同一条物理链路，必然冲突。
帧类型SYNC1PayloadSYNC2长度用途
Mission 0xAA ← 帧头 5 字节 (path+KFS) 0xBB 7B 2区路径规划
Sig 0xCC cmd + chk 0xDD 4B R1 释放信号
Z3 Put 0x55 cmd_id + chk 0xAA ← 帧尾 4B 3区放置指令
Z3 Cmd 0xEE cmd_id+sub+chk 0xFF 5B 停止/取KFS
冲突演示：收到一个 Z3 Put 帧 55 01 54 AA

⚡ 冲突后果链
Z3 Put 帧正常完成 ✅（解析器 idx: 0→1→2→3→4→完成）
但 0xAA 同时触发 Mission 解析器：buf[0]=0xAA; idx=1
Mission 解析器需要再收 6 个字节 才能到达 idx=7 自复位
期间所有新的 0xAA（Mission 帧头）被当成帧内数据 → 真正的 Mission 帧全部丢失
只有等 ErrorRecover 或碰巧收到恰好 6 字节非 0xBB 数据 → 窗口期极短

🔧 修复方向

方案 A：改 Z3 Put SYNC2 为不冲突的值（如 0x66），需 R1 端同步修改。

方案 B：改 Mission SYNC1 为不冲突的值（如 0xAB），需 R1 端同步修改。

方案 C：给 Z3 Put 加独立 UART（不共用 USART10），硬件改动大。

⚠️ 任何方案都需要 R1（发送端）和 R2（接收端）两端同时改。

2

跨 UART 错误连锁复位 — 一条 UART 出错，全部解析器陪葬

bsp_uart.c:154-163
致命
HAL_UART_ErrorCallback 将 USART1、USART3、USART10 三个独立串口的错误处理捆绑在一起。任意一个出错 → 重置所有串口的帧解析器。
/* bsp_uart.c:154 — HAL_UART_ErrorCallback */ else if (huart == &huart1 || huart == &huart3 || huart == &huart10) { R1UartRxDispatch_ErrorRecover(); // 三个串口共用一个恢复！ }
/* r1_uart_rx_dispatch.c:44 — 一次调用，全部清零 */ void R1UartRxDispatch_ErrorRecover(void) { R1Link_ErrorRecover(); // 重置 USART10 全部 4 个解析器 R1LinkZ3CmdLink_ErrorRecover(); // 重置 USART1 解析器 R1UartRxDispatch_Start(); // 重开两路 IT 接收 }
⚡ 触发场景
USART1 或 USART3 RX 引脚悬空 → 持续 FE/NE 噪声错误
每个错误触发 ErrorCallback → R1UartRxDispatch_ErrorRecover()
USART10 的 4 个解析器被反复清零 → 永远凑不满一个完整帧
即使 USART10 硬件完全正常，也收不到任何数据

🔧 修复方向

方案 A：拆分为独立的 ErrorCallback 处理，USART1 错误只复位 USART1 的解析器，USART10 错误只复位 USART10。

方案 B：如果 USART1/USART3 在当前硬件上未使用，直接禁掉（红外分支的做法）。

3

帧完成早退 → 后续解析器丢字节 → 帧被"饿死"

r1_link.c:269-298
致命
R1Link_OnRxByte 将同一个字节串行喂给 4 个解析器，但任一解析器完成帧就 return——排在后面的解析器根本收不到这个字节。
/* r1_link.c:269 */ void R1Link_OnRxByte(uint8_t b) { // 解析器 #1: Mission 帧（优先级最高） if (r1_r2_connect_rx_feed_byte(&s_rx_ctx, b, frame7) != 0U) { r1_link_on_mission_frame(frame7); return; // ← 早退！#2/#3/#4 解析器吃不到 b } // 解析器 #2: Sig 帧 if (r1_link_sig_rx_feed_byte(&s_sig_rx_ctx, b, frame4_sig) != 0U) { r1_link_on_sig_frame(frame4_sig); return; // ← 早退！#3/#4 解析器吃不到 b } // 解析器 #3: Z3 Put 帧 if (r1_link_z3_put_rx_feed_byte(&s_z3_put_rx_ctx, b, frame4_z3_put) != 0U) { r1_link_on_z3_put_frame(frame4_z3_put); return; // ← 早退！#4 解析器吃不到 b } // 解析器 #4: Z3 Cmd 帧（优先级最低，最容易被饿死） if (r1_link_z3_cmd_rx_feed_byte(&s_z3_stop_rx_ctx, b, frame5_stop) != 0U) { r1_link_on_z3_cmd_frame(frame5_stop); } }
⚡ 具体场景：Mission 帧完成时，Sig 解析器正好 idx=2
Sig 解析器状态：已收 CC 01，idx=2，等待第 3 字节 CD
当前字节 0xBB → Mission 帧完成 → 早退 → Sig 解析器没收到 0xBB
Sig 解析器停在 idx=2（状态不变）
下一字节 0xCC（下一个 Sig 帧的帧头）→ 被当成 idx=2 的数据存入 buf[2]
再下一字节 0xCD → 存入 buf[3] → 检查 buf[0]==0xCC && buf[3]==0xDD → 失败！
旧的 Sig 帧丢失，新 Sig 帧的帧头被破坏 → 两个帧都丢了

🔧 修复方向

去掉早退（return），改为：所有 4 个 feed_byte 都执行完，只用一个局部变量记录"是否有帧完成"。最后统一处理完成的帧。

⚠️ 注意：同时可能有多个解析器完成（极少见但理论上可能），需要定义优先级。

4

HAL_UART_Receive_IT 返回值被丢弃 — 静默停摆

r1_uart_rx_dispatch.c:31-35
严重
/* r1_uart_rx_dispatch.c:31 */ static void r1_uart_start_rx_it(UART_HandleTypeDef *huart, uint8_t *rx_byte) { (void)HAL_UART_AbortReceive(huart); __HAL_UART_CLEAR_FLAG(huart, UART_CLEAR_OREF | UART_CLEAR_NEF | UART_CLEAR_FEF | UART_CLEAR_PEF); (void)HAL_UART_Receive_IT(huart, rx_byte, 1U); // 返回值被丢弃！ }
若 HAL_UART_Receive_IT 返回 HAL_BUSY（RxState ≠ READY）或 HAL_ERROR，RXNE 中断不会再触发，USART10 进入静默停摆状态。由于返回值被 (void) 丢弃，调用方完全不知道接收失败。

在 ErrorRecover 频繁调用的场景下，HAL_UART_AbortReceive 可能未完全清理 HAL 内部状态（尤其在中断上下文中），后续 Receive_IT 失败概率增大。

🔧 修复

检查返回值，若失败则重试或上报错误计数，至少记录到 g_r1_link_dbg 中方便 Keil Watch 诊断。

5

Z3 Put 帧缺少帧层去重

r1_link.c:222-231
严重
对比其他三种帧，Z3 Put 帧在 r1_link_on_z3_put_frame 中缺少帧级去重检查：
// Mission 帧 — ✅ 有去重 if (R1LinkDedup_IsDuplicate(r1_link_dedup_ch_z2_mission, fp, HAL_GetTick()) != 0U) { return; // 重复帧，跳过 } // Sig 帧 — ✅ 有去重 if (R1LinkDedup_IsDuplicate(r1_link_dedup_ch_z1_sig, fp, HAL_GetTick()) != 0U) { return; } // Z3 Put 帧 — ❌ 无去重，直接往下走 s_z3_put_ok++; r1_zone3_parse_from_link_z3_put(cmd.cmd_id, frame4[1]); // 无去重保护
虽然 r1_zone3_parse_post 内部有去重（与 Z3 Cmd 共用 r1_link_dedup_ch_z3_cmd 通道），但①调试计数器 s_z3_put_ok 会虚增，②重复帧白白传到应用层才丢弃，浪费 CPU。

🔧 修复

参照 Mission/Sig 帧的模式，在 r1_link_on_z3_put_frame 中加去重：
fp = R1LinkDedup_FpZ3Cmd(R1_LINK_Z3_PUT_WIRE_CMD_ID_PUT_L3, frame4[1]);
if (R1LinkDedup_IsDuplicate(r1_link_dedup_ch_z3_cmd, fp, HAL_GetTick())) return;

6

Mission 解析器 idx==7 复位时 buf 残留可能产生假帧

R1_R2_connect.c:315-335
中等
当 Mission 解析器到达 idx=7 但帧无效（buf[6] ≠ 0xBB），idx 被重置为 0，但 buf[0..6] 的旧数据未被清除。
if (ctx->idx == R1_R2_CONNECT_FRAME_BYTES) // idx == 7 { ctx->idx = 0U; // 只复位索引，不清空 buf！ if (ctx->buf[0] == 0xAA && ctx->buf[6] == 0xBB) { ... } if (b == 0xAA) { // 0xAA 重启采集，覆盖 buf[0] ctx->buf[0] = b; ctx->idx = 1U; } // else: buf 保留旧数据，下次 0xAA 只覆盖 buf[0] }
极端场景：buf 残留 AA xx xx xx xx xx BB（恰好是之前某个无效帧的数据），新的 0xAA 覆盖 buf[0]，后续 6 字节恰好覆盖 buf[1..6] 且 buf[6]=0xBB → 产生一个合法的假帧。概率极低但非零。

🔧 修复

idx 复位时 memset(ctx->buf, 0, sizeof(ctx->buf))，或至少清掉 buf[6]。

🏗️ 架构级结论

这不是单点 bug，而是协议设计层的冲突：4 种帧共用一条 USART10 物理链路，但：

  • 同步字节有重叠（0xAA 一身二职）→ 帧解析器状态机互相污染
  • 解析器串行但有早退 → 优先级低的帧被"饿死"
  • 错误恢复全局化 → 一个 UART 的噪声能瘫痪另一个 UART
  • 返回值不检查 → 静默失败无法诊断

就近可修 Bug 2~6。Bug 1（0xAA 冲突）需要 R1+R2 两端协议同步修改。
